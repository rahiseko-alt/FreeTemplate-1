# setup（AGENTS.md の「未記入」を埋める）

ゴールは **ルート `AGENTS.md` の「コマンド」欄と「規約」欄から「未記入」を無くすこと**。
埋める値は **実在のコードから読み取る**。想像で書かない。該当が無い欄は **「なし」** と書く
（空欄のまま残さない。「なし」も確定した情報として扱う）。

**分岐の選択肢をユーザーに並べて選ばせない。** 下記の判定条件で自分で決める。

## 0. プロダクトのコードの所在を確認する

1. `git branch -a` で全ブランチを確認し、**プロダクトのコード**がどこにあるかを特定する。
   - **同梱サンプル（`apps/web`、`packages/ui`）はプロダクトのコードとして数えない。**
   - 割り当てられた作業ブランチが空でも、他のブランチにプロダクトがある場合がある。
2. プロダクトが既定ブランチ以外にしかない場合は、**そのブランチに切り替えて（または、そこから
   作業ブランチを切って）作業する**。既定ブランチへ揃えるかどうかは、この時点では扱わない。
3. 分岐：
   - **プロダクトがある** → 「A. 取り込み」を実行する。
   - **プロダクトが無い**（同梱サンプルのみ）→ ユーザーが新しくアプリを作り始めるときだけ
     「B. ゼロから始める」に入る。**それ以外は、欄を「未記入」のまま残して、指示された作業を
     そのまま行う**（サンプルのコマンドを「コマンド」欄に書かない。サンプルはプロダクトではない）。

## A. 取り込み（プロダクトのコードがある）

ユーザーの確認を取らずに次を実行し、**やったことを事後に報告する**。順に実行する。

1. **「コマンド」欄を埋める**：実在のコードから実際のコマンドを読み取り、ルート `AGENTS.md` の
   「コマンド」欄に書く。読み取り先は `package.json` の scripts / `Makefile` / `pyproject.toml` /
   `Cargo.toml` / CI 定義など、**そのプロダクトが実際に使っているもの**。
   - **開発サーバ**：ローカルで起動する1コマンド。
   - **テスト（全件 / 1件だけ）**：1件だけ走らせる形（ファイル指定・名前指定）も必ず書く。
     デバッグのたびに全件回すのを避けるため、この2つは別々に要る。
   - **lint / 型チェック**：それぞれのコマンド。型が無い言語なら型チェックは「なし」。
   - **必須の環境変数**：**名前だけ**を列挙する。**値は書かない**（`.env*` は Git 管理外）。
     `.env.example` / 起動時に読まれる変数から拾う。無ければ「なし」。
   - **共通の文言・値の置き場所**：ユーザー向け文言・定数・設定値を集約する1ファイル（または1ディレクトリ）を
     特定して書く。既存に無ければ**1つ作って**そのパスを書く（`AGENTS.md`「結合を増やさない」1 が
     参照先を必要とするため、「なし」にはしない）。
   - **規約**：既存コードで書き方が既に1つに定まっているもの（命名・ディレクトリ配置・エラーの返し方など）を
     1行ずつ足す。定まっていないものは書かない。
2. **引継ぎ記録の一本化**：プロダクトが既に独自の引継ぎ記録（`memory.md`、`docs/progress.md`、
   `docs/session-reports/` 等）を持つ場合は、**それを正とする**。`docs/handoff.md` にはその参照先を
   1行書くに留める（二重管理しない）。`docs/handoff.md` に別プロジェクトの記録が残っていれば、
   要約せず破棄して初期化する。
   **`docs/failures.md` は append-only。取り込みでも消さない。**
3. **CI をこのプロジェクトのものにする**：`.github/workflows/` を実際のコマンドで緑になるよう書き換える。
   - `ci.yml`：集約ゲートの **job `name: ci-green` は必ず維持する**（branch protection と
     `scripts/setup.sh` がこの名前に依存しており、変えると必須チェックが永久 pending になって
     全 PR がマージ不能になる）。
   - **緑にするためにチェックを削る・弱めるのは禁止**（`AGENTS.md`「完了の証明」は CI の書き換えにも
     等しく効く）。実行内容は入れ替えてよいが、**型 / Lint / テスト / ビルド / 依存監査**の各段は残す
     （「コマンド」欄に無いビルド・依存監査も、CI には残す）。
   - `codeql.yml` の `languages`、`prod-smoke.yml` の `PROD_URL`（全ブランチの push で走る）、
     `.github/dependabot.yml` の `package-ecosystem` を、このプロジェクトの実態に合わせる。
     対象が無いワークフローは削除する。
4. **同梱サンプルの削除**：`apps/web`、`packages/ui` と、**それ専用の設定ファイル**を削除する。
   放置すると無関係な起動確認で CI が恒久的に赤くなる。ただし：
   - **プロダクトのコードが作業ツリーに実在することを確認してから行う**（他ブランチにしか無い
     状態で判定しない）。
   - プロダクトが同じ構成を使っている場合（例：プロダクト自身が pnpm / TypeScript）、
     `pnpm-workspace.yaml`・`pnpm-lock.yaml`・`tsconfig.base.json` 等は**プロダクトの資産なので残す**。
   - **判断が付かないファイルは削除せず残す。** 削除は独立したコミットで行い、後から戻せるようにする。
5. **不要な PR の整理**：同梱サンプル向けの依存更新 PR（Dependabot 等）が残っていれば閉じる。
   `auto-merge.yml` は緑の PR を自動 squash マージするため、放置すると無関係な更新が既定ブランチに入る。
6. **既存コードは変えない**：構成・依存・アーキテクチャは維持し、欄を埋めるための最小変更に留める。
7. **機械強制の確認**：下記「C. 機械強制の有効化」が未適用なら、この取り込みの一環として実施する
   （Public 化の可否だけはユーザーに確認する）。

## B. ゼロから始める（プロダクトのコードがまだ無い）

**プロダクトのコードがまだ無い場合のみ**適用する。既にコードがある場合は「A. 取り込み」に従い、
この節（および下記の鉄板構成）は**適用しない**。スタックを勝手に仮定せず、必ず次の順で進める。

1. **ヒアリング** — スタックの項目をゼロから聞き出さない（非エンジニアには答えようがない）。
   下記「鉄板構成とヒアリングFAQ」に従い、**鉄板構成から外れる理由があるかどうか**だけを、
   非エンジニアにも即答できる言葉で確認する。
2. **リサーチ** — FAQで鉄板から外れる分岐が発生した項目についてのみ、その制約の範囲で
   最新のベスト構成を調べる（全問「いいえ」で鉄板のまま進める場合はリサーチ不要）。
3. **提案** — 具体的なスタックを **1 案（＋根拠、＋代替 1 つ）** で提示する（鉄板のままなら
   「鉄板構成のままで進めます」の一言でよい）。
4. **承認** — ユーザーの明示的な OK を取る。**黙って進めない**。
5. **設定** — 承認された構成で雛形を作り、**その実コマンドを `AGENTS.md`「コマンド」欄に書く**
   （手順 A-1 と同じ形式）。**実装作業の実行はこの後**。

### 鉄板構成とヒアリングFAQ（非エンジニア向け）

**鉄板構成**（ゼロから始める場合の初期値。既存プロダクトには適用しない）：

- クラウド / ホスティング: Vercel
- 言語 / ランタイム: TypeScript（strict） / Node.js 22
- フレームワーク: Next.js（App Router） + React
- パッケージ / 依存管理: pnpm（workspace）
- DB / データアクセス: 無し（必要になってから追加）
- 認証: 無し（必要になってから追加）
- IaC / デプロイ: Vercel（push で自動デプロイ）
- テスト: Vitest
- CI: GitHub Actions（同梱の `.github/workflows/ci.yml`）
- Lint / フォーマッタ: ESLint

この構成の記入済み実例が `apps/web/AGENTS.md`。パッケージ管理・IaC・テスト・CI・Lint は
クラウド/言語が決まれば自動的に付随するものなので、個別にヒアリングしない
（＝非エンジニアに聞いても答えが出ない項目は、そもそも質問にしない）。

**ヒアリングFAQ（分岐点だけを聞く。全問「いいえ」なら鉄板のまま）**：

1. **クラウドの縛り**：「会社や顧客から『このクラウドを使うこと』と既に決まっていますか？
   （例：AWSやAzureを契約済み、社内規定で指定されている）」
   - いいえ → 鉄板のまま（Vercel）。
   - はい → 指定のクラウドに合わせて構成を再提案する（例: AWSなら Amplify Hosting、
     Azureなら Azure Static Web Apps 等）。
2. **既存システムとの接続**：「今作るものは、社内の既存システム（基幹システム・社内DB等）と
   同じ場所に置く／つなぐ必要がありますか？」
   - いいえ → 鉄板のまま。
   - はい → 既存システムのクラウド・ネットワークに合わせる（質問1と連動して再提案）。
3. **ログイン機能**：「使う人がログイン（会員登録・パスワード等）する必要がありますか？」
   - いいえ → 鉄板のまま（認証なし）。
   - はい → 追加で確認：「使う人は社員だけですか、社外の人も含みますか？」
     - 社員だけ → 会社で使っている Google/Microsoft アカウントでログイン（SSO）。
     - 社外も含む → メールアドレス等での一般的なログイン（Auth.js 等）。
4. **データの保存**：「入力した内容を保存して、後で見返したり検索したりする必要がありますか？」
   - いいえ → 鉄板のまま（DBなし）。
   - はい → 追加で確認：「保存するデータの形は、表計算ソフトの表のようにきっちり決まって
     いますか、それとも案件ごとに変わりますか？」
     - きっちり決まっている → 表形式のデータベース（PostgreSQL 等）。
     - 案件ごとに変わる → 柔軟な形式のデータベース（MongoDB 等）。
5. **言語・技術の縛り**：「会社やチームで『この言語・技術を使うこと』という決まりはありますか？」
   - いいえ → 鉄板のまま（TypeScript / Next.js）。
   - はい → 指定の言語・技術に合わせて鉄板を再構成する。

未確定のまま残った項目は「未定」と明記し、決まり次第埋める。

## C. 機械強制の有効化（新しいリポジトリで1回だけ）

既定ブランチ `main` に branch protection を掛け「CI が緑でないとマージ不可」にする。
**クローンで運ばれない唯一のサーバー側設定**で、これを掛けて初めてルール文に歯が付く
（未設定だと、赤い PR や AI の auto-merge が main に入り得る）。以下は実地検証済みの手順。

- **a：リポジトリを Public にする（前提）** — GitHub 無料プランの **Private では branch protection /
  Ruleset は強制されない**（設定画面に「Team org にしないと効かない」旨の警告が出る＝実地で確認済み）。
  公開してよいかは**必ずユーザーに確認する**。公開しない場合は歯止めが掛からないので、代わりに
  `auto-merge` を無効化し、マージは必ず人手で行う。
- **b：`main` に「`ci-green` が緑でないとマージ不可」を掛ける。経路は2つあり、Public ならどちらでも効く**
  （どちらか一方でよい。**GitHub の現行 UI は既定で (A) Rulesets に誘導する**ので、そのまま (A) を使うのが迷いが少ない）。
  - **(A) Rulesets（現行 UI の既定・推奨）**：Settings → **Rules → Rulesets** → 「New ruleset」→「New branch ruleset」。
    **ハマりどころ4点（ここを外すと"作ったのに効かない"状態になる＝実地で確認済み）**：
    1. **Enforcement status を『Active』にする**（既定は **Disabled** のまま。Disabled だと一切適用されない）。
    2. **Target branches → 「Add target」→「Include default branch」を選ぶ**（未設定だと画面上部に
       「does not target any resources / **Applies to 0 targets**」と出て適用されない。1 target = `main` になればOK）。
    3. **「Require status checks to pass」にチェック → 検索欄で `ci-green` を追加** → 緑の「**Create**」で保存。
    4. **「Require a pull request before merging」にもチェックし、Required approvals は `0` のままにする**
       （承認人数を上げない）。**これが無いと、上の3点を掛けても `main` への直 push で CI を丸ごと
       迂回できてしまう**（実地で確認済み＝最重要）。
  - **(B) 従来の Branch protection（代替）**：Settings → 左メニュー **『Branches』** →「Add branch protection rule」→
    **Branch name pattern に `main`**（空だと Create が押せない）→「Require status checks to pass before merging」に
    チェック → 検索欄で **`ci-green`** →「Require a pull request before merging」にもチェック（Required approvals は
    classic API/UIでは 0 を選べないため、代わりに Required approvals を **1** にするか、(A) Rulesets を使う → 一番下の緑「**Create**」。
  - ⚠ **(A)(B) いずれも無料 Private では強制されない**（理由・対処は上記 a を参照）。
- **c：Secret Protection / Push protection を有効化する** — Settings → **Security → Code security**
  （旧 Security and analysis）→「Secret Protection」「Push protection」をそれぞれ **Enable**（Public repo なら無料）。
  未有効だと、誤って API キー等をコミットしても検知・ブロックされない（実地で確認済み＝ボタンが「Enable」表示なら未有効）。
  依存の自動更新は `.github/dependabot.yml` が同梱済みなので追加設定は不要（PR を1本出せば自動的に動き出す）。
  取り込みでスタックが変わった場合は `package-ecosystem` を実際の依存管理に書き換える（手順 A-3）。
- **エンジニア（任意）**：gh CLI 認証済みなら `bash scripts/setup.sh` で `ci-green` を一括適用も可。
- ⚠ GitHub Actions の自動トークン（`GITHUB_TOKEN`）には branch protection を変える権限が無く、workflow
  ボタンでの自動化は不可（過去に試みて startup failure。`docs/failures.md` 参照）。必ず人の管理者権限で行う。

## 確認せずに進めること / 必ず確認すること

**確認せずに進める**（いちいち聞かない）:

- 上記「A. 取り込み」の全項目。CI・ワークフローの書き換え、同梱サンプルの削除、サンプル向け PR の整理を含む。
- 既存スタック上での通常の実装・修正・テスト追加。
- lint / 型チェック / テストを緑にするための修正。
- プロダクトが既に使っている依存管理ツールを、CI や「コマンド」欄として採用すること。

**必ず確認する**（ユーザーにしか判断できない、または取り消しが効かない）:

- **リポジトリを Public にする**（公開は取り消しが効かない）。
- 秘密情報の扱い、外部サービスへのデータ送信、課金が発生する追加。
- プロダクトのコード・履歴の破棄（force push、ブランチ削除、指示のない大規模リファクタリング）。
- プロダクトのクラウド事業者 / 言語 / フレームワークの変更。
- **新規の**依存ライブラリ追加、パッケージマネージャーの混在（理由を添えて提案する）。

チェックインでは、上の「必ず確認する」項目を**議題として持ち出さない**。作業に必要になった時点で確認する。

## モノレポで package ごとに構成が違う場合

その場合だけ、対象ディレクトリに `AGENTS.md` を置いて上書きする（雛形は `presets/_TEMPLATE.md`）。
より深いディレクトリの `AGENTS.md` が優先され、書いていない項目だけルートを継承する。
単一プロダクトならルート `AGENTS.md` の「コマンド」欄だけで足りる。
